# D7 migration plan: UUIDv7 primary keys

**Status:** proposal, not yet executed beyond Phase 1. Written for the Product Owner's confirmation of the phasing and the one open design question in Phase 4, before any further phase starts.

D7 was accepted as a decision on 2026-09-24 and SPIKE-03 (`README.md`, `benchmark-results.json`) confirmed its premise: UUIDv7 gives a real, measurable B-tree locality benefit over the current scheme. What remains is executing the cutover without breaking a system that is already running, tested and (for Phase 0) merged to `master`. This plan exists because that cutover is not one change — it is several, with very different blast radii — and the decision proposal itself only committed to "migrations switch `text` keys to `uuid` before the schema freeze," not to how.

## What is, and is not, in scope

D7 is about **our own generated primary/foreign key IDs** — not every text column that happens to look like an identifier.

**In scope** (we generate these; nothing external depends on their current shape):
- `tenant.tenant_id` (also the FK on all 12 RLS-protected tables — see `tests/integration/support/tenant-isolation.ts`'s `TENANT_TABLE_FIXTURES`)
- `audit_event.audit_event_id`
- `foundation_proof_record.proof_record_id`
- `approval_request.approval_id`
- `outbox_event.event_id` / `event_delivery.event_id` (already carried in the CloudEvents-shaped envelope as `id` — `platform/event-envelope`)
- any new Phase 1+ table's own generated primary key

**Out of scope** (each has its own, separate governance):
- `Idempotency-Key` (`idempotency_record.idempotency_key`) — decision D2 already fixes this as a client-supplied RFC 9562 UUID of *any* version, validated at the HTTP boundary. D7 doesn't touch it.
- `actor_id`, `provider_id`, `role_code`, `action_type`, `consumer`, `credential_id` — these identify something outside our own key space (an IdP subject, a configured provider, a role/action name, a consumer name, a token's own `jti`). None of them are a *generated* primary key we control the shape of.
- Row-level `bigint GENERATED ALWAYS AS IDENTITY` columns (`outbox_event.entry_id`) — already exactly what D7 wants (monotonic, dense, locality-perfect) for their purpose (dispatcher lease ordering); nothing to change.

## Why one migration is not the right shape

The tables above aren't independent — `tenant_id` is a foreign key on every one of them, `current_setting('app.tenant_id')` is compared against it in every RLS policy, it is the `sintius_tenants` JWT claim value, and it appears in every route path (`/v1/platform/tenants/{id}`, `X-Active-Tenant`). Converting it is a wire-contract change (JWT claim shape, URL shape), not an internal refactor. The others (`audit_event_id`, `proof_record_id`, `approval_id`, outbox `event_id`) are internal-only — never in a URL, never in a JWT — so they carry essentially none of that risk. Treating all of D7 as one migration would force the highest-risk part (`tenant_id`) to block the lowest-risk, highest-value part (everything else), and would force one enormous, hard-to-review diff touching RLS policies, every module's persistence adapter, every HTTP test fixture and the tenant-isolation gate's fixtures all at once.

## Proposed phases

**Phase 1 — done, this spike.** `platform/id` (UUIDv7 generator, RFC 9562, tested and mutation-checked) and the SPIKE-03 benchmark. No schema changed.

**Phase 2 — adopt for new tables only, starting with Phase 1 billing domains.** Every new table from here forward (Customer Management, Product Catalog, Pricing Engine, …) gets a `uuid` primary key generated by `platform/id`'s `generateUuidV7()`, from its first migration. Zero risk to existing tables, zero test churn on Phase 0 — this is the change that actually matters for "before Phase 1 adds billing tables" (the handover's own framing): it is cheaper to start every new table right than to retrofit it. Ships as part of each Phase 1 module's own first PR, not as a standalone migration.

**Phase 3 — retrofit the internal-only Phase 0 IDs.** `audit_event_id`, `proof_record_id`, `approval_id`, outbox/delivery `event_id`. One migration per table (checksum-protected, forward-only, per this repo's convention), each: add a new `uuid` column generated by `platform/id`, backfill existing rows (`gen_random_uuid()` is fine for backfill — the locality property only matters for *future* inserts, not historical rows), switch the primary/foreign key and every `WHERE`/`JOIN` in the module's persistence adapter, update `platform/event-envelope`'s `id` field documentation (its type was always "string," so this is compatible), update the money/architecture/isolation-gate fixtures that reference these IDs, and update every test that asserts an exact literal ID shape. Bounded per-table blast radius; each table is its own reviewable PR. No API or JWT contract changes — these IDs are never in a URL or a claim today.

**Phase 4 — `tenant_id` itself. Needs a Product Owner decision before it starts, not just an implementation call.**

The decision text says tenants get "a UUIDv7 primary key plus a separate unique, human-readable slug" — two fields, not a type change on one. That means deciding what the *external* surface (URLs, the `sintius_tenants` JWT claim, `X-Active-Tenant`) addresses a tenant by, since the two fields can't both be "the identifier" at the wire boundary:

| Option | External surface addresses a tenant by | Trade-off |
|---|---|---|
| **Recommended: keep the slug external.** | The existing human-chosen slug (renamed from `tenant_id` to `tenant_slug` internally; the wire shape of `/v1/platform/tenants/{id}`, `X-Active-Tenant` and the `sintius_tenants` claim is unchanged — same strings tenants and support already use) | Every RLS policy, FK and index moves to the new internal `uuid` column; authentication resolves slug → uuid once per request (a single indexed lookup, the same shape `PostgresTenantPersistence` already does for other lookups) and binds the uuid as `app.tenant_id` for RLS. Zero breaking change to any existing client, test fixture, JWT issuer configuration or the demo script. This is the option I'd implement absent a reason to prefer the other. |
| Switch the external surface to the raw `uuid`. | The new UUIDv7 value | Matches "the PK is the identifier" more literally, but breaks the API contract (`tenant_id` in request/response bodies and the URL path changes shape), breaks the JWT claim contract (every identity-provider configuration issuing `sintius_tenants` would need to switch from slugs to UUIDs), and invalidates the wording of `docs/pre-implementation/13-api-specification.md` wherever it documents `tenant_id`. Needs coordination with whichever identity-provider product is eventually chosen (still an open item, HANDOVER_PROMPT_CODEX.md §5 item 2). |

Once that's confirmed, Phase 4 touches: migration 001 (`tenant` and its 11 dependent tables' FK type), `platform/tenant-context` (the `TenantId` branded type and every resolver), `modules/identity-tenant` (provisioning/lifecycle commands, the authentication service's claim mapping, `PostgresTenantPersistence`), `apps/api` (route params, `X-Active-Tenant` handling), `tests/integration/support/tenant-isolation.ts` (`TENANT_TABLE_FIXTURES`), and every file that references a tenant ID (46 files match `tenantId(|tenant_id` across the repo today, most of them tests) — genuinely a multi-PR effort, sequenced table-by-table like Phase 3, with the isolation gate re-run in full after every step since it is the release-blocking control for exactly this kind of change.

## What this spike did not do

It did not touch any existing migration, table, or test. `platform/id` is a new, unused-by-anything-else package until Phase 2 adopts it. `npm run check` is unaffected in every respect except the new unit tests it now also runs.
