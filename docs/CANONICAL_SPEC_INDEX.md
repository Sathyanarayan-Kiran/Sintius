# Canonical Implementation Specification Index

**Purpose:** This repository contains two independent, complete pre-engineering documentation suites for the same platform — [`docs/pre-implementation/`](pre-implementation/README.md) (deliverables 00–25, driven by `AI_Native_Subscription_Revenue_Platform_Master_Product_Specification.md`) and [`docs/pre-engineering/`](pre-engineering/SUB-INDEX_Document_Register.md) (`SUB-0000`–`SUB-0021`, driven by `Subscription_Platform_Pre_Engineering_Documentation_Master_Prompt.md`). Both are internally consistent, both reached Draft v0.1 completion, and both cover the same domain with largely (but not entirely) agreeing content, different ID schemes, and different depth in different places.

This document is the **single entry point for implementation**. It does not replace either suite — both remain the detailed reference, and neither is edited by this reconciliation. Instead, it declares, topic by topic, which suite is authoritative, what the other suite adds on top, and resolves the handful of places where the two genuinely disagree rather than merely differ in format.

**How to use this index:** for any implementation question, find the topic below, read the declared primary source, and check the supplementary note before assuming the primary source is complete on its own.

## 1. Reconciliation principles

1. Non-destructive: neither suite is edited. This index is the only new artifact.
2. Pointer-based, not a rewrite: where the two suites agree (the large majority of content), this index says so once and points to either as equivalent — it does not re-derive already-correct material.
3. Real conflicts are resolved explicitly, with a decision recorded (§3), not silently picked.
4. Real gaps (one suite has depth the other lacks) are declared as an explicit adoption, not left for an implementer to discover by accident.
5. Terminology is unified going forward (§2): new code, tickets, and commit messages use the canonical term only.

## 4. Consolidated non-negotiable invariants

Both suites converge on the same invariant set; this is the single merged list (supersedes restating it per-document going forward):

1. Never double-charge because of retries (idempotency-record + unique business constraints).
2. Never lose an accepted usage event (durable write before acknowledgement).
3. Never silently mutate a posted invoice, ledger entry, activated price version, or historical commercial snapshot (corrections only, via adjustment/credit/reversal/superseding version).
4. Never allow one tenant to read, change, infer, cache, search, or receive another tenant's data (RLS + mandatory application filter, defense in depth).
5. Never create a financial effect without stable source identity, idempotency, authorization, audit, and lifecycle lineage.
6. Never use binary floating point for commercial calculations.
7. Never let external provider state names become canonical domain states.
8. Never let search, analytics, graph, cache, or AI projections authorize or post financial state.
9. Never generate a financial explanation from AI memory — only from calculation traces and verified Revenue Lifecycle Graph facts.
10. Never store raw payment credentials or secrets in normal application storage, logs, traces, events, or audit diffs.
11. Never allow an AI action to change customer financial state without policy, authorization, evidence, approval where required, and audit — and never above its declared autonomy level (SUB-0016 §2).

- **Local snapshot:** `docs/decision-ledger.html` (single-browser, exports edits as JSON for hand-back)

**Five items were flagged `blocking: true`.** As of 2026-09-23 all five carry `status: decided`, but with two materially different resolution shapes — see [HANDOVER_PROMPT_IMPLEMENTATION.md](HANDOVER_PROMPT_IMPLEMENTATION.md) Step Zero for how each is actually handled:

2. `stripe-scope` — **Deferred into a gated implementation task**, not a concrete answer: "Propose options ahead of implementation." A Stripe-scope proposal is required before the Payments module (`SUB-E009`) is finalized.
3. `rounding-proration` — **Deferred into a gated implementation task:** "Propose options during implementation." A rounding/proration proposal is required before the pricing engine's golden dataset is frozen (Phase 1 exit).
4. `ai-autonomy-thresholds` — **Deferred into a gated implementation task:** "Propose options during implementation." A per-agent autonomy proposal is required before any AI agent is enabled above L0 (read-only insight).
5. `backend-runtime` — **Deferred into a gated implementation task, but time-critical:** "Propose options during implementation." SPIKE-01 is now the literal first activity of Phase 0 — repo scaffolding cannot proceed past it without a picked runtime.

None of items 2–5 should be read as "no longer a concern" — they are downgraded from *pre-implementation hard stop* to *first-class task with its own confirm-before-proceed gate*, per the Product Owner's explicit choice to proceed this way rather than pause further.

1. Every genuine conflict between the two suites identified during this reconciliation (§2: `PriceComponent`/`PriceRule`, `Receivable`, `RiskAssessment`) has an explicit, one-directional resolution — no "either is fine" left on a real conflict.
2. Every topic in §3 names exactly one primary source; a supplementary source is named only where it adds material the primary lacks.
3. No content from either suite was deleted, edited, or duplicated by this index — it is purely a cross-reference and conflict-resolution layer.
4. The consolidated invariant list (§4) is a strict union of both suites' invariant lists with no invariant dropped.
5. This index is kept current if a future session adds a new document to either suite or resolves a Decision Ledger item that changes a §2/§3 entry.
